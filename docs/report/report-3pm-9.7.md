# Diagnosis: "Worker PUT failed 403: {"error":"Forbidden"}"

## Where the 403 actually comes from

The `{"error":"Forbidden"}` JSON body is emitted by **the Cloudflare Worker itself**, not Backblaze B2 ('cloudflare-worker/src/index.ts:259'). B2 errors would arrive as XML (`<Error>...InvalidAccessKeyId...</Error>`) and would be proxied through verbatim with B2's status, not the JSON shape in the exception. So this is an **authorization-layer rejection inside the Worker**, ruling out at the outset:

- **CORS** — would fail the preflight/request in the browser layer; the PUT here is a native `HttpClient` call from Flutter, which doesn't enforce CORS, and the work anyway responds to OPTIONS with permissive headers.
- **WAF / Cloudflare rules** — the response is generated by the worker's own code path.
- **B2 bucket policy / key permissions** — B2 is never reached; the request is blocked before signing.

The request reached `isAuthorized == false` in `checkDocumentAuthorization()` (index.ts:24–89).

## Root cause (primary): upload happens before `file_path` is written

The Worker authorizes `documents/...pdf` objects **only** by exact-match query on Supabase:

```
GET /rest/v1/documents?file_path=eq.<objectPath>&select=id   →  must return ≥1 row
```

But the client upload sequence in `lib/features/documents/services/scan_service.dart` (`uploadNewDocument`, lines 111–153) is:

1. `_createDocument(...)` — inserts the documents row **without** `file_path` (likely NULL).
2. `_uploadPdf(objectPath, pdfBytes)` — the PUT hits the Worker → Worker's `file_path=eq.documents/xxx.pdf` query returns `[]` → **403**.
3. `_updateDocument(... filePath)` — `file_path` is only set **after** the upload (lines 144 vs 147–152).

The DB state at the moment of the PUT never satisfies the Worker's authorization predicate, so every new-document upload is guaranteed to 403. This is a logical race between the write path and the authorization check — a broken invariant introduced when reads/writes were migrated to the Worker proxy.

## Secondary candidate causes (in decreasing likelihood)

1. **RLS on the `documents` table.** The Worker queries with the user's JWT + anon key, so Supabase RLS applies. If the user lacks a SELECT policy on `documents` (or the policy depends on `room_members` joins that fail), the query returns `[]`/non-OK → 403. Confirm by running the REST query as that user.
2. **Missing/malformed Bearer token.** `WorkerClient.putBytes` must set `Authorization: Bearer <access_token>`; missing header or an expired JWT (Supabase returns 401 from REST, handled as `!response.ok → false`) both yield the same generic 403 with no distinguishing signal.
3. **Path mismatch.** The regex is `^documents/(.+)\.pdf$` and the match uses URI-decoded equality; if `_buildObjectPath` ever produces a path with characters that `encodeURIComponent` mangles differently than stored, the match silently fails. (Less likely; paths are ID-based.)
4. **Scan-page path branch** (`pages/{docId}/{n}.jpg`) — not in play here since the failing PUT is the PDF, but it shares the same fragment: it requires a `scan_pages` row to pre-exist.

## Recommended verification (before fixing)

Add distinguishing detail temporarily, or check Worker logs (`wrangler tail`) with a debug log in each early-return branch of `checkDocumentAuthorization`. The zero-change verification is simpler:

```sql
-- as the uploading user, at the moment of failure:
select id, file_path from documents where id = '<document_id>';
-- expect: file_path IS NULL  ← confirms root cause
```

## Candidate fix

Reorder/set state so the authorization predicate holds before the PUT: set `file_path` at `_createDocument` time (path is derivable from `documentId`, so move step 4's `_buildObjectPath` before step 2 and insert the row already containing `file_path`), or relax the Worker to also allow documents whose `id` matches the path segment. Reordering client-side is the minimal, Worker-compatible fix.
